# Patches

AI-powered CSS patch injector for any website. Available as a **Google Chrome extension** (Manifest V3), with the original Electron desktop app still in this repo.

---

## Chrome extension (Manifest V3)

The extension preserves the core Patches workflow — describe a change in plain English, Gemini generates CSS from a trimmed DOM outline, the CSS is applied to the active page, patches are saved per domain and restored on future visits — and adds:

- **Firebase sign-up / login (required)** before any AI prompt or patch mutation. Email + password, password reset, sign-out. Cloud patch sync to Firestore using the same `users/{uid}/data/patches` schema and user-scoped `firestore.rules` as the desktop app.
- **A persistent floating Patches launcher** on the right edge of webpages that **toggles** Chrome's **native side panel** (`chrome.sidePanel.open` / `chrome.sidePanel.close`) — clicking the icon opens it, clicking again closes it (auth screen when signed out; prompt + patch management when signed in). No toolbar click needed, and the panel never covers webpage content — Chrome narrows the page's viewport so the site reflows around it.
- **Light sage-green branding** (Brilliance `#FDFDFD`, Misty Marsh `#D2E1D5`, Clouded Pine `#608463`, Copper Patina `#9DB9A0`, Paying Mantis `#709674`) applied through shared design tokens in the side panel and popup; the official `build/patchesnewlogo.png` logo generates the toolbar icon set.

### Architecture

| Electron app | Chrome extension |
| --- | --- |
| `main.js` IPC handlers | `extension/background/index.js` — MV3 service worker (message router, AI coordination, auth gates, cloud sync) |
| AI pipeline in `main.js` (`generateCSSFromPrompt`, `sanitiseCSS`, `parseModelAspects`, system prompt) | `extension/background/patchAgent.js` (ported, logic unchanged) |
| `lib/geminiClient.js` retry/fallback client | `extension/background/geminiClient.js` (ported as an ES module) |
| `lib/geminiKey.js` key validation | `extension/background/geminiKey.js` |
| Firebase Auth in `renderer/auth.js` (compat SDK, Electron window) | `extension/offscreen/` — **offscreen document** hosting the modular Firebase SDK (esbuild-bundled), because MV3 service workers cannot use IndexedDB which persistent auth sessions require |
| `loadCloudPatches` / `saveCloudPatches` (`users/{uid}/data/patches`) | same schema, called from the offscreen document via Firestore |
| `storage/patches.json` per-domain patch store | `chrome.storage.local` (`patches` key, same data shape) in `extension/background/patchStore.js` |
| Inline DOM outline builder injected via `executeJavaScript` | `extension/content/patches-content.js` content script (runs natively in the page) |
| `<style id="patches-N">` injection | single `<style id="patches-extension-styles">` element per page |
| Settings window (`.env` key) | popup settings view; key lives in `chrome.storage.local`, never in the bundle |
| Command bar + patches panel + toast | popup (`extension/popup/`) **and** Chrome's native **side panel** (`extension/panel/`) reusing the existing design tokens |

```
extension/
  manifest.json          # MV3: storage/activeTab/scripting/offscreen/sidePanel + http(s) hosts; side_panel.default_path
  background/            # ES-module service worker ("type": "module")
    index.js             # message router, auth relay + gates, generate-patch, cloud sync, open-side-panel
    patchAgent.js        # system prompt, CSS sanitiser, aspect parser (from main.js)
    geminiClient.js      # Gemini REST client w/ retries + model fallbacks (from lib/)
    geminiKey.js         # AQ./AIza key validation
    patchStore.js        # chrome.storage.local persistence (patches/settings/auth)
  offscreen/
    offscreen.html       # hosts the auth bundle (MV3 offscreen document)
    offscreen.bundle.js  # generated by scripts/build-offscreen-auth.js (do not edit)
    auth-entry.js        # source: Firebase Auth email/password + Firestore sync
  content/
    patches-content.js   # apply/revert CSS, restore on revisit, page outline
    launcher.js          # floating sage-green launcher (closed Shadow DOM) → asks the worker to toggle the native panel
  panel/                 # extension-origin page rendered in Chrome's native side panel — the
    panel.html|css|js    # actual Patches UI (auth screen, prompt, patch list); the page reflows
                         # of the webpage are managed by Chrome, never by scripts
  popup/                 # popup.html/css/js — same UX as the side panel, gated by auth
  icons/                 # generated from build/patchesnewlogo.png (16/32/48/128)
```

**Auth flow:** side panel/popup → background (`auth-sign-in` / `auth-sign-up` / `auth-send-reset` / `auth-sign-out`) → offscreen document (Firebase) → `onAuthStateChanged` broadcast cached in `chrome.storage.local` (`auth` key). Protected messages (`generate-patch`, `delete-patch`, `reset-domain-patches`, `set-patch-aspect-enabled`, `toggle-patches`, `save-api-key`) are rejected by the service worker with `authRequired` unless signed in — enforced in the background, not only in the UI. When a session restores (Firebase persists it in the offscreen document's IndexedDB across browser restarts), patches sync: cloud-preferred merge in, local-only patches push out, matching the desktop's `mergePatchesPreferCloud` behaviour.

**Side panel/launcher flow:** the content script injects one small host element — the floating sage-green launcher button (closed Shadow DOM, keyboard-accessible, at the vertical right edge; always visible on supported pages). Clicking it **toggles** the panel. GESTURE-CRITICAL: `chrome.sidePanel.open()` keeps the click's user-gesture context only when it is the FIRST extension call on the message path (an awaited storage read in the worker before `open()` invalidates it — the root cause of a previous "panel no longer opens" regression). The launcher therefore reads the persisted state itself (`chrome.storage.local`) and commands the worker with `open-side-panel` or `close-side-panel`; the worker calls **`chrome.sidePanel.open({ tabId })`** as its very first extension call, or **`chrome.sidePanel.close`** across the known scopes (Chrome exposes `sidePanel.close()` plus `onOpened`/`onClosed` events — verified on Chrome ~137+; built and tested on Chrome 155).

Open-state tracking is event-authoritative, never inferred from `getOptions()`: top-level `sidePanel.onOpened`/`onClosed` listeners fire for programmatic opens, other open paths, and the user's manual ✕, and each event is mirrored to `chrome.storage.local` (`panelOpen` key) so a restarted service worker never acts on a stale default. Rapid repeated clicks re-read the fresh state each time and alternate cleanly. Because `sidePanel.close()` resolves even when nothing was open, a real close is confirmed with the `onClosed` lifecycle event: no event within a short window means the tracked state was stale → the worker answers `corrected`, persists closed, and the launcher immediately re-requests an open within the same click's gesture — so a manual ✕ (or any missed event) never costs more than nothing.

Chrome resizes the webpage's viewport; Patches displays its full UI in `panel/panel.html`. The panel page uses `chrome.tabs` to resolve the focused tab, is an extension-origin document so host-page CSS/keyboard handlers cannot reach it, and follows tab switches while open (`chrome.tabs.onActivated` re-reads the domain and patch list).

Security posture: the Firebase web config is public-by-design client config (same policy as the desktop app); Firestore access is user-scoped by `firestore.rules` (`request.auth.uid == userId`) — never bypassed client-side. The user's Gemini key is entered at runtime and stored only in `chrome.storage.local`; AI requests are made exclusively from the service worker. AI output is validated (fences stripped, brace check, size cap) before being placed in a `<style>` element; no AI- or page-controlled JavaScript is ever executed.

### Install & run locally

```bash
npm install
npm run build:extension   # esbuild-bundles the offscreen Firebase auth docs + copies to dist/extension
# → dist/extension  (dist/extension/offscreen/firebase-config.json is copied from the repo root)
```

Then in Chrome:

1. Open `chrome://extensions`.
2. Enable **Developer mode** (top right).
3. Click **Load unpacked** and select the `dist/extension` folder.
4. Browse to any website — the floating launcher appears at the right edge. Click it to toggle Chrome's native side panel; create an account or sign in to patch.

For development you can also load the unpacked extension directly from `extension/` (source) instead of `dist/extension`; the copy in `dist/` is just the reproducible build output.

### Configure

**Firebase (already wired to the repo's `firebase-config.json`, project `patches-1`):**

1. Firebase Console → **Authentication → Sign-in method**: **Email/Password must be enabled** (if it is not, sign-up fails with the actionable error `auth/operation-not-allowed`).
2. **Firestore Database**: create it if absent; deploy `firestore.rules` from this repo (`users/{userId}/data/{docId}` scoped to `request.auth.uid == userId`). The extension never writes outside `users/{uid}/data/patches`.
3. Authorized domains: none needed for email/password. If Google sign-in is added later, add the extension's origin handling and a browser redirect page — see limitations.

**Gemini (per browser, in popup → ⚙ Settings):**

- **API key** — create a free key at <https://aistudio.google.com/apikey>. Google now issues keys starting with `AQ.`; legacy `AIza…` keys are accepted by the checker but Gemini rejects standard keys as of September 2026.
- **Model** — defaults to `gemini-3.8-flash`, with `gemini-3.7-flash`, `gemini-3.6-flash`, `gemini-3.5-flash-lite` as automatic fallbacks on 429/503.

There is no `.env` for the extension; nothing secret is bundled.

### Testing

```bash
npm i --no-save puppeteer-core   # test-only dependency, not added to package.json
npm run build:extension
node scripts/test-extension.js
```

Launches a real headless Chrome, loads the unpacked extension via Chrome's `Extensions.loadUnpacked` CDP command (branded Chrome 137+ removed `--load-extension`), and asserts — against the **real** Firebase project configured in `firebase-config.json`:

- the MV3 module service worker starts,
- a patch seeded into `chrome.storage.local` is applied by the content script on page load; toggling patches off/on reverts and re-applies CSS without a page reload; the content script returns a `PAGE_OUTLINE` DOM snapshot for AI context,
- the floating launcher auto-injects exactly once (survives re-injection; no overlay sidebar/iframe remains), a real click routes to `chrome.sidePanel.open({ tabId })` (call-recording wrapper in the service worker), and the **toggle state machine** (open → close → open, rapid clicks, stale-state recovery) passes deterministically via success doubles of `open`/`close` — the real-gesture OPEN path cannot be driven by CDP clicks (no user activation headlessly) and is verified manually,
- the former "Show floating launcher" setting is fully removed; the launcher is always visible on supported pages and stale `launcherEnabled` preferences are ignored,
- the native panel page shows the sign-in screen signed out, has no overlay close button (Chrome owns close), and accepts the `@` keystroke typed physically into the email field,
- unauthenticated users cannot submit prompts or mutate patches (`authRequired`), while the patch list stays readable,
- **real sign-up** (throwaway `qa-<timestamp>@patches.test`), sign-out, sign-in, and password-reset flows against Firebase Authentication,
- the patch map is **pushed to Firestore** (`users/{uid}/data/patches`) after a signed-in mutation,
- a signed-in account without an API key gets the actionable `needsApiKey` flow,
- the popup shows the sign-in screen signed out and product UI + account chip signed in,
- no uncaught page errors.

Note: the test hits the shared Firebase project and creates one throwaway Firestore document per run (`users/{uid}/data/patches`). Password-reset emails to the `patches.test` domain are accepted by Firebase but never delivered.

### Functionality tested & known limitations

All flows above were executed (28/28 passing at the time of writing); the AI path reuses the desktop pipeline (identical prompt, sanitiser, aspect parsing, retry/fallback logic). Gemini generation itself still needs **your** API key entered in Settings — a credential cannot be shipped.

- **Google sign-in is not implemented.** It requires the Google provider enabled in Firebase Console plus a redirect-based OAuth flow (MV3 popups cannot be used from content scripts / offscreen documents). Email/password fully works; add Google later via `signInWithRedirect` on a dedicated extension page.
- **Only per-domain patch sync is cloud-backed.** The auth cache is local to the browser by design; open/close of the native panel is owned by Chrome itself.
- **Sticky notes (page understanding) still not ported** — secondary feature, deferred by design.
- **Canvas / Gmail / Notion:** the launcher, side panel, and patch application work, but frequently-changing / virtualized DOMs can make generated selectors stale, and Gmail's iframed documents need patching per frame root. Verify per site.
- **School / work networks:** some of them block generative-AI endpoints, which surfaces as “Patch failed → Network problem” during generation. Patches now shows an actionable message with a **Try again** button instead of the raw “Failed to fetch”; generating a patch on a phone hotspot usually confirms the diagnosis. The service worker also runs a keepalive during long AI calls so MV3 idle termination cannot kill mid-flight requests.
- **`chrome://` pages, Chrome Web Store, PDF viewer:** Chrome blocks injection; the launcher simply does not appear and the popup shows the unsupported-page notice.
- Pages open *before* the extension loads get the launcher via a fallback `chrome.scripting.executeScript` injection the first time Patches is opened on that tab.

## Desktop app (Electron)

### Setup

```bash
npm install
```

### Firebase (login & cloud storage)

Patches uses Firebase for user authentication and syncing patches to **Cloud Firestore**. As the developer, you should set up your own central Firebase project so beta testers can seamlessly sign up inside the app.

1. Create a project at [Firebase Console](https://console.firebase.google.com/).
2. **Authentication** → Sign-in method → enable **Email/Password**.
3. **Firestore Database** → Create database (production mode is fine).
4. Deploy security rules from `firestore.rules` in this repo (Firebase CLI: `firebase deploy --only firestore:rules`, or paste into the Rules tab).
5. **Project settings** → Your apps → add a **Web** app.
6. Copy the configuration values into `firebase-config.json` in the root of this repository.

By placing your Firebase config in `firebase-config.json`, the credentials will be bundled into the packaged Electron app. Beta testers will simply see a **Sign in** / **Sign up** screen upon launching the app and will be authenticated against your central Firebase project without needing to configure their own backend. 
(Note: You can still use `.env` for local testing if you prefer).

### Set your Gemini API key

Get a key at <https://aistudio.google.com/apikey>

Google AI Studio now creates **authorization keys** that start with `AQ.`. As of September 2026 the Gemini API **rejects standard `AIza…` keys**. Create a new key in AI Studio, then:

```bash
# create a .env file in the project root
echo "GEMINI_API_KEY=AQ.your_api_key_here" > .env
npm start
```

Settings accepts both `AQ.` (new) and `AIza` (legacy) prefixes. Prefer an `AQ.` key.

Patches sends the key as an `x-goog-api-key` header (not a `?key=` query parameter).

### Choose a model (optional)

Default: `gemini-3.8-flash`. Shut-down IDs (e.g. `gemini-2.0-flash`, `gemini-2.0-flash-lite`) return 404 on every request, and deprecated 2.5 IDs 404 on many newer keys; use the list below or call the API [ListModels](https://ai.google.dev/api/rest/v1beta/models/list) for your key.

```bash
export PATCHES_MODEL="gemini-3.8-flash"
```

Supported in the app:
- `gemini-3.8-flash`
- `gemini-3.7-flash`
- `gemini-3.6-flash`
- `gemini-3.5-flash-lite`

Note: thinking models spend output tokens on reasoning, so the app sets `maxOutputTokens: 8192` — `max_output_tokens` covers thinking + answer, and small caps truncate responses (`finishReason: MAX_TOKENS`).

## Usage

Sign in first, then browse and patch sites.

- **New patch** (navbar, ⌘K)  →  AI prompt bar in the center (what you use to *create* a patch)
- **Notes** (navbar, ⌘⇧N)     →  Same prompt bar, routed to sticky notes for this page
- **Saved** (navbar, ⌘⇧P)     →  Right sidebar: list, aspect checkboxes, **Reset site**, remove
- Toggle switch →  Enable/disable all patches

## How the LLM pipeline works

1. Grabs a structural outline of the live DOM (tags, id/class/role, short text).
2. trimDOM() also prepares a trimmed HTML snapshot for context.
3. Sends to Gemini: system prompt asks for a **JSON** object `{"aspects":[{"label","css"},...]}` so independent changes (e.g. dark mode vs font size) can be toggled separately in the patches panel.
4. Each aspect’s CSS is validated (braces, `!important` where needed); legacy patches with a single `css` field still work as one aspect.
5. Combined enabled aspects are injected as `<style>` tags, saved under `storage/patches.json` per domain.

### Page notes (prompt-driven)

Use **Notes** (⌘⇧N) like **New patch**: type what you want pinned (e.g. “show popular videos”). Patches builds a redacted outline once, sends it **with your prompt** to Gemini, and overlays **one grouped sticky note** whose entries (title + snippet, sorted by importance) each keep their anchor — click an entry to scroll to that element on the page. Refresh re-runs the last prompt. There is no background page reading. User-initiated notes are capped at 30 requests per domain per hour. Raw page text is not saved; the group note's position is stored locally.

Render-time anchor diagnostics: main.js logs `[patches:notes] anchor <n> …: FOUND/MISSING on page at render time` for every item, so if the target page re-renders between outline capture and the Gemini response (anchors gone), it's visible in the console.

### Color requests (“blues → reds”)

The snapshot does **not** include colors from external stylesheets, so the model cannot see every blue hex on the page. The prompt instructs it to use **hue-rotate / filter** on the root when a broad recolor is needed, plus targeted rules for classes/ids that appear in the snapshot. Results vary by site; try rephrasing (e.g. “strong red theme via filter on html”) if one attempt is weak.

### End-user API key setup

`.env` is intentionally excluded from installers. Beta users add a key in **Settings** (recommended) or create `.env` manually. Without a key, the browser and **saved** patches still work; only **New patch** (AI generation) needs a key.

- macOS packaged app: create `.env` at `Patches.app/Contents/.env`
- Windows packaged app: create `.env` in the same folder as `Patches.exe`
- Supported fallback: `%APPDATA%/Patches/.env` on Windows or `~/Library/Application Support/Patches/.env` on macOS

Required content:

```env
GEMINI_API_KEY=AQ.your_api_key_here
```

Legacy `AIza…` keys may still be stored locally; Gemini itself rejects standard keys as of September 2026. Use a new authorization key from AI Studio.

If no key is found on launch, Patches opens **Settings** (always-on-top) and the main window. You can browse and use saved patches; add a key to enable AI patch generation.

### Unsigned beta builds

For beta distribution without code signing:

- macOS: right-click the app and choose **Open** to bypass Gatekeeper.
- Windows: click **More info** then **Run anyway** in SmartScreen.

### Code signing stubs (to enable later)

`package.json` uses unsigned defaults for beta builds. When you are ready to sign, add fields like these under `build.mac` and `build.win`:

```json
{
  "build": {
    "mac": {
      "// signing identity": "Developer ID Application: Your Team",
      "// notarization env": "APPLE_ID / APPLE_APP_SPECIFIC_PASSWORD / APPLE_TEAM_ID"
    },
    "win": {
      "// cert file": "build/certs/windows-signing.pfx",
      "// cert password env": "CSC_KEY_PASSWORD"
    }
  }
}
```
